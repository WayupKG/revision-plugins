# Память проекта в Revision

Revision — общая память проекта: следующий, кто придёт (человек или агент), узнает из неё, что
решено и почему. Инструменты — в MCP-сервере `revision`.

**Правило одно: читай, прежде чем предлагать, и записывай, когда решено.**

## Шпаргалка

| Когда | Что вызвать |
| --- | --- |
| Начал работу | `what_changed` — кратко; вся группа — `kind`, с причинами — `detail` |
| Собираешься предложить или поменять подход | `search_knowledge` с `types: ["DECISION"]` |
| Решение принято, причина сбоя найдена, приём замечен | `remember` — сразу, с `rejected`, `paths`, `commit` |
| Опираешься на запись с полем `code` | `git log <commit>..HEAD -- <paths>` → `confirm_memory` |
| Меняешь то, на что опираются другие | `get_document` / `get_decision` → `backlinks` |
| Правка кода сделала документ неверным | `edit_document` с `why` |
| Закоммитил работу по задаче | строка `Revision: KEY` → `link_commits` |
| Нужна задача или смена статуса | `create_task_draft`, `update_task_draft` |

## 1. Начало работы
Вызови `what_changed`: новые и заменённые решения, закрытые и сдвинутые задачи, правленые документы с
прошлого визита. Опирайся на это, а не на то, что помнишь из прошлых разговоров.

Подключение из файла в репозитории (`/mcp/projects/<id>`) уже привязано к проекту — `project_id` не
нужен. Подключение общее и неясно, о каком проекте речь, — `list_projects` и спроси человека.

## 2. Прежде чем предлагать
Спроси `search_knowledge` по решениям. Отвергнутое заново не предлагай. Предлагаешь изменить
принятое — назови это решение прямо: «Это меняет решение «…», принятое потому, что …».

Черновик задачи и `remember` сами приносят похожие решения (`decisions_to_check`,
`similar_decisions`) — прочитай их, прежде чем продолжать.

## 3. Записывай, когда решено
Сразу, не в конце: контекст может оборваться. Но только **решённое** — человек согласился или выбор
уже сделан в коде. Варианты ещё обсуждаются — не пиши. Просят подождать или ничего не записывать —
не пиши, даже если решение кажется очевидным.

Проверка перед записью: **пригодится ли это через месяц тому, кто не видел этого разговора?**
Нет — не пиши.

| `kind` | Что | Заголовок — утверждение |
| --- | --- | --- |
| `decision` | выбрали одно вместо другого | «Выкладка через rsync, а не Git» |
| `debugging` | причина сбоя и как её узнать | «Поиск падал на разделителе таблицы — tsquery stack too small» |
| `pattern` | приём, который стоит повторять | «Секреты в тестах — через фикстуру, а не env» |
| `observation` | факт о проекте, не решение | «Прод-база — PostgreSQL 18 с pgvector» |

- Заголовок — утверждение, а не тема: не «Деплой», не «Проблема с поиском».
- `why` — самое ценное поле: почему так, а не иначе.
- У решения — `rejected`: что отвергли и почему (`[{option, why}]`). Сервер предупредит
  (`rejected_match`, `rejected_before`), если отвергнутое предложат снова, — скажи об этом человеку.
- `paths` — файлы, на которые запись опирается, и `commit` — текущий `git rev-parse HEAD`.
- `body` — коротко: суть, где в коде, ссылки на связанное.
- Папка по теме есть (`list_documents`) — передай её в `folder`.
- **Никогда** не записывай ключи, пароли, токены и значения из `.env` — только имя переменной.

Несколько записей сразу (итог работы, перенос) — **один** `remember` с `items`, до 50 за вызов: каждый
вызов — шаг модели по всему контексту. Ответ — счётчики и `problems`.

`remember` ответил `similar_decisions` (или они пришли в `problems`) — это не записано:
- новое отменяет одно из показанных → повтори с `supersedes: <id>`;
- это о другом → повтори с `checked: true`;
- противоречит решению, которое человек не отменял → не записывай, спроси человека.

## Сверка с кодом
Запись пришла с полем `code` (`paths`, `commit`, `verified`) — прежде чем на неё опереться, проверь:
`git log --oneline <commit>..HEAD -- <paths>`.
- Изменений нет или запись всё ещё верна → `confirm_memory` (`id`, `commit` — текущий HEAD).
- Код поменял суть → поправь запись: новое решение с `supersedes`, заметку — `edit_document`.

## 4. Связи
В тексте записей и документов ссылайся на то, на что опираешься:
`[[Название]]` — документ или решение, `[[KEY-42]]` — задача, `[[Название|подпись]]`.
- Причина сбоя → на решение или документ, где её исправили.
- Решение → на задачу, из-за которой его приняли, и на документ, который оно меняет.
- Ссылка на то, чего ещё нет, допустима: цель найдётся, когда появится.

Меняешь то, на что опираются другие, — сначала посмотри `backlinks` (`get_document`, `get_decision`)
и `mentioned_in` (`get_task`).

Битые ссылки — одним `broken_links`; все цели чини одним `relink` с `pairs`. Документы по одному
ради ссылок не открывай.

## 5. Документы
- Оглавление — `list_documents` (названия по папкам, `folder` — одна папка), текст и `version` —
  `get_document` по названию.
- Изменил в коде описанное в документе — поправь `edit_document`: `old_text` дословно и один раз,
  несколько мест — одним вызовом в `edits`, `why` обязателен (это сообщение версии).
- `version_conflict` — перечитай и повтори, не пиши поверх.
- Новый документ — `create_document` с путём папки: `folder: "Инструкции/Сервер"`.

## 6. Коммиты
- Коммит по задаче — строка `Revision: KEY` в конце сообщения (рядом с `Co-Authored-By`).
- Затем `link_commits`: коммиты — из `git log --format='%H%x1f%an%x1f%aI%x1f%B%x1e'`,
  `repository` — `git remote get-url origin`. Хостинг не важен, повтор безопасен.
- `git blame` привёл к коммиту со строкой `Revision:` — открой `get_task`: там причина и решения.

## 7. Задачи
Задачи меняются черновиком. Ответ `status: PENDING` — задачи ещё нет: скажи человеку подтвердить её в
Revision («Ждут вашего подтверждения» на главной или вкладка «Задачи» проекта).
Ответ `status: APPLIED` — человек разрешил менять задачи сразу, изменение уже сделано: назови, что
именно ты изменил.

## Чего не делать
- Не пересказывай разговор в памяти — только то, что пригодится следующему.
- Не дублируй: перед `remember` проверь `search_knowledge`, нет ли такой записи.
- Не выдумывай проекты, ключи и id: инструмент ответил «не найдено» — так и скажи.
- Не подменяй отказ обходом: `forbidden` — у человека нет права, скажи ему об этом.
